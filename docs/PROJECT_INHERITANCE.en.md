# Project Inheritance

Chinese version: [PROJECT_INHERITANCE.md](./PROJECT_INHERITANCE.md)

`pantheon-ops` inherits through a complete Pantheon Base snapshot plus a declarative business overlay. An upgrade rebuilds the product tree from the official Base release locked in `foundation-release.lock.json` and injects Ops-owned business assets. It does not patch an old tree file by file or maintain shared-source allowlists.

## Ownership

- `pantheon-base` owns `platform`, `system/*`, shared backend/frontend, generators, and product engineering configuration.
- `pantheon-ops` owns `business/bizscope`, `business/cmdb`, `business/deploy`, business smoke, business design, and repository identity.
- `business-overlay.json` is the only machine-readable asset and assembly manifest.
- `.business-overlay-report.json` records the Base commit, Ops file hashes, generated files, and import rewrites.

The rebuilt tree keeps the Base layout and Go module identity `pantheon-base`. Injected business imports are rewritten from the historical `pantheon-ops/backend/...` prefix to `pantheon-base/...`; shared source is never rewritten to an Ops module identity.

## Assembly Points

Business modules attach through static overlay registries generated by the Ops rebuilder:

- `backend/modules/business/business_overlay_registry.go`
- `frontend/src/modules/businessOverlay.ts`
- `frontend/src/core/router/businessOverlayComponentRegistry.ts`
- `backend/modules/system/iam/menu/business_overlay_component_registry.go`

The rebuilder wires these static registries into Base aggregation points. Base `generated_*` registries remain exclusively owned by the low-code generator and may be regenerated or purged without carrying built-in Ops registrations. Each business module owns its migrations, menu and permission seeds, runtime i18n seeds, and API routes.

Base's menu-contract gate (`check-menu-contract.mjs`) discovers component registry files by name convention (frontend `*Registry.ts`, backend `*registry.go`), so `businessOverlayComponentRegistry.ts` / `business_overlay_component_registry.go` are automatically included in the consistency check without registering a file list on the base side.

## Upgrade

Run these commands from the Ops repository root:

```powershell
# Query GitHub for the latest stable official Base release, download four assets,
# verify SHA256, manifest and immutable tag, then update the Ops lock.
# With no version argument this selects latest; this handoff pins v0.18.5.
npm run fetch:base-release -- --release pantheon-base-v0.18.5

# Rebuild and verify a temporary consumer from the pinned official release.
npm run rebuild:from-base -- --target .tmp/clean-base-overlay
node scripts/business-overlay/check-business-overlay.mjs --root .tmp/clean-base-overlay
npm run check:shared-drift -- --root .tmp/clean-base-overlay

# Run backend CGO race, frontend, business smoke and hosted gates before applying.
```

The weekly GitHub workflow uses this same latest-release acquisition and pinned reconstruction. Rebuild and drift checks verify official GitHub assets and compare extracted snapshot bytes; they never read an enclosing Git HEAD. Local Base source arguments are rejected. An explicit `--release` must fetch that published version and cannot fall back to latest or another tag. Cached archives must match the lock and official release SHA256; extracted trees are regenerated from verified archives to prevent stale or modified files from becoming the baseline.

## Prohibited

- Do not publish Base patches merely to extend a consumer allowlist.
- Do not copy Base release-producer tooling into Ops.
- Do not rewrite the complete Base tree to a `pantheon-ops` Go module.
- Do not retain generic product files absent from `business-overlay.json`.
- Do not replace the current Ops tree before staged verification.

This baseline replacement is an L2 human gate. Required validation includes overlay tests/checks, Windows Go race with CGO, frontend lint/type/build, business smoke, and SonarCloud revision/size/duplication review.

## 8. Business data migrations

Canonical business SQL lives under `backend/modules/business/<module>/.../migrations/`, with six-digit versions and paired `.up.sql` / `.down.sql` files. `businessMigrations` explicitly lists sources covered by `businessPaths`. The Ops rebuilder derives the fixed `backend/pkg/database/migrations/` destinations and records them as generated files, retaining the Base startup migration failure behavior.

Business ownership cannot claim `backend/pkg/database` or arbitrary destinations. Missing pairs, duplicate versions/directions, invalid sources and Base version collisions fail reconstruction. Only unpublished business migrations may be renumbered; published migration collisions require a separately designed compatibility upgrade. The unpublished host-state backfill uses `000032`; Base retains `000031`.

## 9. Go dependency graph assembly

After adding `goDependencies` to the official Base snapshot, reconstruction loads the complete package and test dependency graph before hashing the output report. The normalized `backend/go.mod` and `go.sum` are generated files; missing packages, checksums or loading errors abort reconstruction without a success report.

Validate the emitted tree directly with `go list -buildvcs=false -mod=readonly -deps -test ./...` and applicable builds/tests. Do not repair module files with `-mod=mod` during acceptance. Verified release assets and the root lock identify archive provenance; enclosing-repository VCS stamping is disabled. Insufficient offline caches must be populated before rebuilding, rather than skipping dependency validation. Official release and full race/business-smoke gates still apply.
