# pantheon-ops 项目现状综合评审报告

## 执行摘要

**pantheon-ops 目前还不能算“阶段性交付完成”：功能面铺得很广、代码量与测试量都不小，但试点交付尚未验收，并且存在若干已在源码中确认的权限与远程执行边界问题。** 这个判断与项目自己的记录一致：仓库的 `.harness/STATUS.md` 明确写着“试点交付尚未验收完成”，10 个交付工作包（C01–C06、E01–E04）全部处于 planned。

- **基线**：main 的 HEAD `71c86cf`（2026-11-16），业务代码约 45,390 行源码、19,119 行测试（后端，`backend/modules/business/*`）。
- **外部两份报告**：共 16 项发现（SEC 8 + ARC 1 + DEP 7），我对 SEC-001\~008、ARC-001 和 DEP-001\~007 均回到源码复核，**事实层面全部成立**；我只对个别严重度和描述范围做了调整（见第 4 节）。
- **我自己新增的发现**：资产关系与 Pod→Node→VM 追溯在代码中并不存在；Helm 只是数据库快照记录；Nacos、RocketMQ 在代码里零引用；任务列表接口全表加载后内存分页。
- **不建议推倒重做**：部署、K8s、可观测等主链路有真实实现和测试，问题集中在边界收口与验收缺失。
- **最该先做的事**：修固定模板的参数校验、任务主机明细的数据范围过滤、凭据的归属模型；完成 C01 的后端关联校验；然后在同一候选版本上做真实环境验收。你已确认目标是多租户：业务域目前不参与租户隔离，ARC-001 因此升为 P1，见“多租户目标下的补充评估”。

- **已回源码复核**：标注为“已复核确认”，意味着我读到了对应代码，行为与报告描述一致。

## 多租户目标下的补充评估

**你已确认目标是多租户，因此 ARC-001 升为 P1：登录与系统域的多租户已经就绪，但业务域（主机、集群、部署任务、凭据）目前没有租户隔离。** 这不矛盾：基础平台的多租户确实已完成，只是它的合同把业务域排除在 V1 之外。

### 已就绪的部分

依据项目文档（`docs/TENANT_INITIALIZATION_GUIDE.md`、`docs/api/TENANT_API.md`、`docs/designs/TENANT_RESOURCE_SCOPE_MATRIX.md`），基础平台采用**行级 `tenant_id`** 隔离，有 compat（默认，所有行落在 tenant\_id=0）与 multi 两种运行模式。租户的创建、成员、登录、切换、套餐、归档，以及用户、角色、部门、字典等系统域资源，都已按合同实现。这部分我只读了文档，没有逐项验证系统域代码。

### 未就绪的部分

- **项目自己的文档就是这么写的**：租户初始化指南写明“业务域 V1 不参与多租户隔离”；V2.0-O4 首批只覆盖 5 张 observability 表，并强调“局部 API 测试不代表消费产品已经隔离”。
- **代码印证**：85 个业务模型结构体中，只有 observability 的 2 个模型文件出现租户字段；deploy 只有日志下载走了 `TenantScopedBusinessGroup`；其余业务路由是 `DataScopedGroup`（Token → Casbin → 部门数据范围），不含租户过滤。
- **直接冲突的设计**：凭据表 `biz_deploy_credential_ref` 的名称唯一索引是全局的（`uk_deploy_credential_name_deleted` 建在 `name` 上），两个租户无法使用同名凭据。

### 在 multi 模式下的后果

这是**推断**，我没有搭建双租户环境验证：租户 A 的运维人员，可能看到或操作租户 B 的主机、集群、部署任务，甚至用 ID 调用其凭据。部门数据范围可能间接限制一部分可见性（部门本身是 tenant-owned），但这是副作用而不是隔离机制，**不能当作租户边界**。SEC-002、SEC-004、SEC-005、SEC-006 在多租户下的风险都会放大。

### 建议路径（不引入新技术，复用基础平台已有机制）

1. **先分类，再动代码**：按基础平台的四分类（platform-global / tenant-owned / tenant-overridable / derived）给每张业务表登记，多数业务表预期为 tenant-owned，并登记唯一键的租户内变体。
2. **先做风险最高的表**：凭据、集群（含 kubeconfig）、主机、部署任务及其主机明细、业务域、服务目录。
3. **复用而不是自建**：用基础平台的 `tenant.Scoper` / `WithTenantScope` 做读写过滤，把业务路由组从 `DataScopedGroup` 换成已被 observability 采用的 `TenantScopedBusinessGroup`。
4. **异步链路要透传租户上下文**：部署的 `runAsyncTask`、K8s 同步、告警评估等后台执行没有请求上下文，需要逐一确认租户信息从哪里来。这一点我没有验证。
5. **补双租户对抗测试**：参照 `internal/middleware/tenant_hostile_smoke_test.go` 的做法，对每个租户化的业务模块各补一条“A 租户读写 B 租户资源”的反例。
6. **排期**：队列标题里没有业务域租户化的工作包。它应当排在 C01 之前或与 C01 同步，否则 C01 的服务实例关联校验写完后还要返工加租户条件。

### 1. 路由到权限点

**业务接口的权限绑定只在 3 个模块里注册，其余模块的接口没有绑定。** 这是对照项目自己的合同得出的：`docs/contracts/SYSTEM_IAM_CONTRACT.md:177` 规定，业务接口权限的唯一来源是启动期调用 `permissionroutes.Register` 的注册表。

| 模块 | 路由数（正则估算） | 已注册绑定 | 说明 |
| --- | --- | --- | --- |
| cmdb | 约 28 | 25 条（主机、分组等） | `cmdb/permission_routes.go` |
| observability | 约 4（多为循环注册，估算偏低） | 28 条 | `observability/audit_policy.go` |
| deploy | 约 50 | 3 条，仅任务导出 | `deploy/log_download.go:34` |
| k8s | 约 70 | 0 | 全模块 grep 无注册 |
| cicd | 约 20 | 0 | 同上 |
| service、filedist、bizscope、secrets | 各有路由 | 0 | 同上 |

- **机制**：访问控制按请求路径加方法交给 Casbin 判断（`casbin_middleware.go:37`）。菜单种子里的权限点（如 `business:deploy:task:start`）只决定页面与按钮；角色保存时，系统按绑定表把权限点转成接口策略（`role_policy_sync.go:60`）。基础平台的静态表里没有任何 `business:` 权限点。
- **推断（未运行验证）**：给非管理员角色勾选 deploy、k8s 的权限点，不会生成对应接口策略，所以只有拥有通配策略的管理员，或手工加策略的角色才能真正调用。这是默认拒绝，不会越权，但“细粒度角色”在这些模块里可能用不起来：页面按钮显示了，点下去却返回 403。也可能另有我没找到的授权方式，需要用一个非管理员角色实测。
- **缺少的权限点（已核实种子常量）**：deploy 的权限点里没有凭据（`credentials` 增删改查四个接口）、回滚、目标解析、事件、日志相关的键。这与 SEC-004 相互印证：凭据没有独立的授权边界。
- **团队的自觉**：CMDB 文件注释说明，已发布的 `keyMatch2` 匹配器会让 `GET /hosts/:id` 的策略同时匹配 `export` 路径，所以详情类权限点故意没有注册。这说明团队了解这类“策略被意外放宽”的问题。
- **等级与验证**：交付完整性 P1（条件性）。验证方法：建一个只有 deploy 任务权限点的非管理员角色，分别调用任务列表、启动、取消，看是否返回 403。

### 2. 前端请求拦截器（`api/request.ts`，506 行）

**拦截器设计比较完整，我之前对“失败时静默”的担心基本被它化解。**

- **已核实的行为**：自动附带 CSRF 头；401 时只刷新一次会话（多个请求共用同一个刷新承诺）后重试，失败才跳登录；403 时按需走二次验证再重试；业务错误和网络错误默认都会弹出翻译后的错误提示，除非调用方设置 `skipErrorMessage`；退出登录过程中会抑制认证类提示。
- **对前面结论的影响**：缩容失败等“没有 catch”的写操作，仍会收到全局错误提示，所以 R-15 降为 P3。真正静默的只有显式设置了 `skipErrorMessage` 或空 `catch` 的地方，例如业务范围下拉。
- **潜在问题**：全局默认超时是 10 秒（`request.ts:60`）。我只在可观测（30 秒）和仪表盘（5 秒）里看到超时覆盖，deploy、k8s 业务页面没有覆盖。若同步集群、导入导出、发布等操作服务端耗时超过 10 秒，浏览器会先报超时，而服务端仍在执行，用户可能误以为失败而重复提交。我没有逐个确认哪些接口会超过 10 秒，所以是潜在问题，验证方法是对这些操作做真实耗时测量。

### 3. 可观测页面逐页（关键词统计，不是逐页走查）

### 2. 未绑定的后果

- **机制：** 授权由 Casbin 按“角色 + 路径 + 方法”判断，策略是在保存角色时由权限点生成的。我在系统域、`pkg`、`internal` 里没有找到给普通角色预置的宽泛业务策略。所以没有绑定的接口，非管理员角色默认拿不到策略，请求会被拒绝。

### 5. 深入复核补充（同日，对第 2 节几项的细化）

**结论：SEC-001 的修复比我预期的扎实，SEC-002 和 SUP-08 也有测试和本地实机证据；我只发现 3 个低风险的残余点，没有发现需要升级的问题。** 以下依据是读最新主分支代码和 T03 的证据摘要，没有运行。

- **SEC-001 注入修复（T02）：**
  - 做法是对每个会进入脚本的字段做字符集白名单：路径禁止空白、控制字符、引号、`$`、反引号、`;`、`&`、`|`、重定向、括号、花括号以及 `.`、`..` 段；服务名、主机名、版本号、端口、JVM 参数列表各有独立校验。
  - 创建任务时校验一次，渲染脚本时再校验一次，所以已持久化或导入的旧记录也进不了脚本。密码类参数用单引号转义写入脚本。
  - 我把模板里读取的 19 个参数键与校验清单逐个对照，除了 3 个密码类参数（已转义）外都有校验。有单独的安全测试文件，覆盖路径穿越、危险卸载根和别名写法。
  - **残余点 1（P3）：** 卸载根目录的保护是一份黑名单，只拦 `/`、`/etc`、`/var`、`/usr` 等 19 个顶层目录。`/etc/ssh`、`/usr/lib` 这类子目录不在其中，有部署权限的操作员仍可构造卸载。这符合“操作员本来就有高权限”的假设，但改成“只允许在约定的安装前缀下卸载”会更稳。
  - **残余点 2（P3）：** 部分模板（如 MySQL 安装脚本）把已校验的路径、服务名、端口直接拼进脚本，没有再做 shell 转义。安全完全依赖校验函数不出错。建议渲染时也统一转义，作为第二道防线。
  - **残余点 3（P3）：** 路径校验没有拦截 `*`、`?`、`~`。我查了卸载脚本，变量都在双引号里，不会展开，所以目前不能利用；只是以后有人改成不带引号时会出问题，可以顺手拦掉。
- **SEC-002 任务详情泄露范围外主机（T03）：** 项目证据称已修复：任务读取统一按数据范围过滤主机，列表改为先取可见 ID 再分页，并新增回归测试；代码里能看到范围过滤和对应的越权写拒绝测试。
- **SUP-08 与受限角色：** T03 的证据称新增模板 6、任务 10（不含导出）、凭据 4 个绑定，共 26 个键，每个动作有独立权限点；详情路由因 keyMatch2 问题继续有意不绑定，并有测试锁定。**项目还记录了本地受限角色矩阵 18 项全部通过**，这正是我清单里 V1 要验证的内容。同候选的远端重跑和维护者终验仍然开放。
- **日志 WebSocket 来源检查（T08）：** 规则是：没有 `Origin` 头（非浏览器客户端）放行；设置了 `PANTHEON_ALLOWED_ORIGINS` 时只允许清单内的来源；否则要求来源主机与请求主机一致。这挡住了跨站劫持，没有发现问题。该接口仍然需要登录令牌，我没有核对令牌是否在升级前校验。
