# C04 binding/cluster admission lock continuation

Parent: 2026-11-16-ops-k8s-service-mutations; L2; business/k8s only. Root approved the narrow owner extension to Cluster and Namespace implementation files; other workers own deploy/service, filedist and k8s/helm. Existing In/Out, UID/resourceVersion, permission and provider-error contracts remain unchanged.

Facts: current Service validates the scoped Cluster/Namespace binding before getting the provider client and issuing HTTP operations. That is admission only: no local owner lock survives the provider call. Cluster already serializes Update/Delete/RotateCredential using a row lock followed by its existing MySQL advisory lock. Namespace has no equivalent callback holding binding ownership for the Service operation. A repeated pre-dispatch read would merely narrow this window.

Minimum complexity: reuse the existing owner row-lock query and client-go client pool. Preserve Cluster's existing WithClusterLock row-then-advisory behavior. Add a request-context Cluster callback using the transaction row fence only, supplying the client built from its locked registration and transaction-bound credential read. The new path does not acquire MySQL's session-scoped GET_LOCK: database/sql may auto-roll back a canceled transaction before its deferred RELEASE_LOCK can run, so adding advisory acquisition to this path would create a cancellation cleanup risk. The row fence already serializes Cluster Update/Delete/RotateCredential, which acquire that same row first. Namespace uses the callback to lock its binding row in the same transaction, validate business scope/environment/action against the locked Cluster, and dispatch an owner-provided callback. Service alone performs client-go create/update/delete inside that bounded callback.

New lock order: Cluster row -> Namespace binding row -> provider call; the transaction releases both rows on success, denial, provider error or cancellation. Existing Cluster writers retain Cluster row -> Cluster advisory lock ordering. No independently acquired Namespace transaction or separate connection for credential lookup is introduced. The request's existing 30-second operation context bounds admission SQL and provider dispatch; context cancellation must retain its cause. Reads remain unchanged. Local binding UPDATE/DELETE and Cluster Update/Delete/RotateCredential cannot commit while these rows remain locked. No callback mutates admission metadata.

No schema, frontend, shared-system, capability-contract, credential, foundation or checker changes.

Verification: first add a deterministic real-MySQL regression gating the simulated provider immediately before mutation and use an independent transaction's SELECT FOR UPDATE NOWAIT to prove both owner rows remain locked. A successful lock while dispatch is gated is the meaningful RED. Include allowed create/update/delete, lock release after completion, provider failure and cancellation, and a single-connection client/credential path regression if feasible. Root runs the fresh disposable-MySQL/CGO race commands after relevant writers freeze; executor supplies filters and exact hashes and may run formatting/compile diagnostics. Existing mutation/RBAC/concurrency tests remain required; no PASS is prewritten.

Evidence boundary: SQL plus an in-memory HTTP provider proves local serialization until the bounded provider callback returns. It cannot roll back a write already accepted by Kubernetes, guarantee a remote write did not complete after a transport timeout, serialize direct external kubectl, or replace real roles/environment/live cluster/final C04 acceptance. Those gaps remain explicit. Root owns aggregate evidence/status, final rebuild/full race/runtime and independent review.
